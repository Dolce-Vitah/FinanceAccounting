# Пояснения
В своём проекте я решила не реализовывать большую часть предложенного опционального функционала в условии задания. Вместо этого мною были придуманы другие функции и возможности:
  - Функция, позволяющая за отведённый период определить точные значения расходов и доходов;
  - Функция, позволяющая за отведённый период сгруппировать расходы и доходы по категориям;
  - Функция, позволяющая за отведённый период посчитать средние расходы в день;
  - Фукнция, позволяющая вывести топ (по умолчанию 5) категорий по расходам за отведённый период;
  - Возможность установить лимит расходов на определённую категорию;
  - Возможность логировать все основные операции, связанные с счетами, категориями и операциями.

По умолчанию логирование операций фиксируется в файле logs.txt, который перезаписывается каждую сессию. Файл расположен на одном уровне с Program.cs.
Все используемые сервисы вынесены в отдельные директории.

# Принципы
Как были соблюдены принципы SOLID и GRASP:
- **Low Coupling**: в пример можно привести использование оповещения о превышении лимита расходов, а также использование интерфейсов вместо конкретных классов. Механизм оповещения никак не зависит от своих подписчиков, а просто рассылает оповещения в определённый момент;
- **High Cohesion**: в моём проекте таким примером может послужить реализация аналитической логики с помощью паттерна Стратегия. Каждый класс AverageDailyExpenses, CategoryGroupingStrategy, TopExpensesStrategy, TotalIncomeExpensesStrategy выполняют свою функцию;
- **SRP**: примером служат фасады для управления BankAccount, Category и Operation объектами. Каждый фасад отвечает за свою доменную модель;
- **OCP**: опять можно привести в пример стратегии выбора алгоритмов для финансового анализа: код не нужно модифицировать, а лишь добавить новые классы, осуществляющие другие функции, связанные с анализом данных за период;
- **Liskov**: каждый сценарий основных операций оформлен в виде объекта, но выполянют они разные действия (create, delete, edit) и реализуют общий интерфейс ICommand. Можно подставить любую команду без происшествий;
- **IS**: в проекте присутствуют интерфейсы, предназначенные только для одной цели, например ILogger, ICommand, ICategoryLimitObserver и т.д.;
- **DI**: все модули в проекте зависят от абстракций. Например, ICategoryFacade зависит от ICategoryLimitObservable.

# Паттерны
1. **Фабрика**: реализована абстрактная фабрика IFinanceFactory, которая создаёт объекты Category, BankAccount, Operation в одном месте;
2.  **Фасад**: реализованы фасады IBankAccountFacade, ICategoryFacade, IOperationFacade для работы с доменными моделями;
3.  **Команда**: все основные сценарии по взаимодействию с доменными моделями реализованы в виде команд (ICommand);
4.  **Декоратор**: LoggerDecorator оборачивает упомянутые выше команды и логирует их время выполнения в файл logs.txt;
5.  **Стратегия**: финансовый анализ за отведённый период времени реализован в виде Стратегии: AverageDailyExpenses, CategoryGroupingStrategy, TopExpensesStrategy, TotalIncomeExpensesStrategy подменяют друг друга в зависимости от требуемого анализа;
6.  **Наблюдатель**: механизм оповещения о превышении лимита расходов реализован с помощью Наблюдателя.
